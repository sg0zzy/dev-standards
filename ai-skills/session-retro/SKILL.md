# Improve the workflow

Use available session evidence and relevant project instructions; resolve applicable standards through the project's adoption record. Respect higher-priority instructions. State missing evidence instead of inventing a pattern.

- Identify repeated friction: unnecessary tool calls, missing context, duplicated or conflicting instructions, slow feedback, and avoidable handoffs. Separate observations from inferred causes and recommendations; cite examples or counts where available.
- Inspect the owning skill, standard, project guidance, or command before proposing changes. Distinguish a local project issue from a reusable workflow problem. Avoid turning an isolated incident into a universal rule.
- Prefer the smallest useful correction: remove a redundant instruction, sharpen a context pointer, reuse a command, or automate a recurring mechanical check with a deterministic script/test. Compare the expected benefit with added context and maintenance cost.
- Return only supported improvements, prioritized by impact, with the affected location and a way to measure success (for example, fewer repeated reads or faster validation). No proposed change is a valid outcome when evidence is insufficient.

Propose changes in the conversation. Do not silently edit global standards, skills, or project files. Apply changes only when explicitly requested and only within that scope; a retrospective request alone is not authorization to write files.
